## 모노레포를 쓴 이유가 바뀌었다

모노레포의 장점을 검색하면 대개 이렇게 나온다. 코드 공유가 쉽다, 원자적 커밋이 된다, 의존성 버전이 한 곳에서 관리된다.

전부 맞는 말이고 실제로 도움이 됐다. Prisma 스키마와 DTO를 패키지로 공유하니 서버와 웹의 타입이 어긋나지 않는다. Turborepo 캐시도 체감된다 — 빌드와 배포 시간이 줄었다. 다만 **코드베이스가 작아서 결정적이진 않았다.** 솔직히 이 규모면 캐시가 없어도 견딜 만하다.

정작 만족도가 높은 이유는 따로 있었다.

> **레포 하나만 읽히면 AI가 파악을 잘한다.**

이게 내가 이 프로젝트에서 모노레포를 유지하는 진짜 이유다.

### 맥락이 레포 경계에서 끊긴다

AI에게 코드를 맡길 때 자주 겪는 실패는 **모르는 걸 지어내는 것**이 아니라 **한쪽만 보고 고치는 것**이다.

서버 레포와 웹 레포가 갈려 있으면, 웹에서 API 응답 타입을 고쳐달라고 했을 때 AI는 웹만 본다. 서버 DTO가 어떻게 생겼는지 모르니 응답을 추측한다. 추측이 맞으면 다행이고, 틀리면 타입체크는 통과하는데 런타임에서 깨진다.

한 레포에 다 있으면 이게 안 일어난다. **"이 필드 추가해줘"라고 하면 Prisma 스키마 → 서버 DTO → 공유 타입 → 웹 컴포넌트까지 한 번에 훑고 고친다.** 사람이 네 곳을 기억할 필요가 없다.

혼자 만드는 프로젝트에서 이건 생각보다 크다. **1인 개발의 진짜 병목은 타이핑 속도가 아니라 머릿속에 올려둘 수 있는 맥락의 양**인데, 모노레포는 그 맥락을 사람이 아니라 파일 시스템이 들고 있게 해준다.

> 회사에서는 프론트와 서버가 다른 레포로 갈린 프로젝트도 하는데, 거기서는 **`openapi.json`이 실제 동작과 어긋나 있어도 한동안 아무도 모르는** 일이 실제로 있었다. 레포가 갈리면 계약이 조용히 썩는다.

---

## 서버를 두 개로 나눈 이유

`apps/server`와 `apps/ai-server`. 둘 다 NestJS에 Fastify 어댑터를 쓴다.

나눈 이유는 **커넥션 수명이 다르기 때문**이다.

일반 API는 요청이 오면 수십~수백 밀리초 안에 끝난다. 그런데 AI 발제문 생성은 다르다. 모델이 토큰을 뱉는 동안 **SSE 커넥션이 수십 초 동안 열려 있다.** 이걸 API 서버에 같이 두면, 발제문 몇 개가 동시에 생성될 때 일반 요청이 밀린다.

그래서 처음부터 떼어놨다. 배포에서도 경로로 갈린다.

```caddy
handle /api/*       { reverse_proxy server:3000 }
handle /ai/*        { reverse_proxy ai-server:3001 }
handle /socket.io/* { reverse_proxy ai-server:3001 }   # WebSocket도 AI 쪽
handle              { root * /srv/www; try_files {path} /index.html }
```

### 그런데 ai-server는 1,349줄이다

server가 7,438줄인데 ai-server는 그 5분의 1도 안 된다. 모듈도 하나뿐이다(`discussion`). server는 열둘이다 — `auth`, `group`, `meeting`, `library`, `board`, `notification`, `mail`, `admin`, `user`, `seoji`, `tmdb`, `showcase`.

**서버 하나를 통째로 띄울 만큼의 코드가 아니다.** 컨테이너 하나, 헬스체크 하나, 환경변수 세트 하나가 이 1,349줄을 위해 존재한다.

지금 다시 정한다면 아마 같은 선택을 할 것 같은데, 이유는 다음 절에 나온다. 나눠놓은 덕에 얻은 게 하나 있기 때문이다. 다만 **"SSE 때문에 나눴다"는 설명만으로는 부족하다**는 건 인정해야 한다. 이 트래픽에서 커넥션이 밀릴 일은 아직 없었다.

## 그 분리가 보낸 청구서

나눠놓으면 반드시 따라오는 질문이 있다. **어떤 데이터가 어느 쪽에 속하는가.**

이건 나눌 때 정해지지 않는다. 나중에 드러난다.

### 감상 저장이 실시간으로 안 됐다

모임 화면에서 멤버가 작품 감상을 남기면 다른 멤버 화면에 바로 떠야 한다. 소켓 게이트웨이(`notes.gateway.ts`)는 ai-server에 있다. 발제문 노트 실시간이 이미 거기서 돌고 있었으니까.

처음 구조는 이랬다.

```
[web] → 메인 서버: 감상 저장
              ↓ (HTTP)
       ai-server: "브로드캐스트해줘"
              ↓ (socket)
        [다른 멤버들]
```

**중간의 HTTP 홉이 조용히 끊겼다.** `AI_SERVER_URL`이 안 맞거나 ai-server가 안 떠 있으면 저장은 되는데 실시간만 안 된다. 에러도 안 난다. 저장한 사람은 화면에 자기 글이 보이니 정상으로 보이고, 남들만 못 본다.

커밋 세 개가 연달아 나왔다.

```
feat: 자체 발제하기 폼 + 작품 감상 섹션
fix: 자체 발제 입력칸 개선 + 감상 API 메인 서버 이전 + 소켓 실시간 반영
fix: 감상을 ai-server 단일 관리로 이전(게이트웨이 직접 브로드캐스트) + 본인 수정/삭제
```

**두 번 옮겼다.** 최종적으로 감상 CRUD 자체를 ai-server로 넘겼다.

```
[web] → ai-server: 저장 + 브로드캐스트 (한 프로세스)
              ↓ (socket)
        [다른 멤버들]
```

### 얻은 규칙

> **소켓 게이트웨이를 소유한 서버가 쓰기도 소유해야 한다.**

실시간이 필요한 데이터는 "어느 도메인에 속하는가"가 아니라 **"어느 프로세스가 알려줄 수 있는가"**로 나뉜다. 감상은 도메인상 분명히 모임 데이터고 메인 서버에 있는 게 자연스러운데, 실시간이 붙는 순간 그 자연스러움이 틀린 답이 됐다.

그리고 이건 앞서 말한 **"나눠놓은 덕에 얻은 것"**이기도 하다. 한 서버였으면 이 문제 자체를 못 만났고, 따라서 이 규칙도 못 얻었다. 값을 치렀지만 배운 것도 있다.

## 안 쓰는 확장을 깔았다가 걷어낸 이야기

처음 설계에는 **추천 기능**이 있었다. 이 사람이 좋아할 만한 책이나 영화를 골라주는 것. 방식도 정해뒀다 — 자체 DB를 만들고 작품을 임베딩해서 벡터 검색으로 유사한 것을 찾는다.

그래서 1기 스키마에는 이게 있었다.

```prisma
datasource db {
  extensions = [pgvector(map: "vector")]
}

model ... {
  embedding      Unsupported("vector(1536)")?
  groupEmbedding Unsupported("vector(1536)")?
}
```

`Unsupported`는 Prisma가 그 타입을 모른다는 뜻이다. 벡터 검색은 `$queryRaw`로 직접 SQL을 써야 한다.

**지금 스키마에는 없다.** 전면 개편(①편의 그 커밋) 때 같이 나갔다.

### 왜 뺐나

기술이 안 돼서가 아니다. **데이터를 모을 방법이 없었다.**

추천이 작동하려면 작품 데이터가 충분히 있어야 하고, 그 작품들의 설명이나 리뷰가 있어야 임베딩이 의미를 갖는다. 국내 도서·영화 데이터를 그만큼 모으는 건 개인 프로젝트에서 현실적으로 막힌 문제였다. (이 벽은 ④편에서 다시 나온다. 넉 달 뒤에 같은 자리에 또 부딪힌다.)

그러면 남는 건 **동작하지 않는 기능을 위해 확장 하나와 컬럼 셋을 들고 있는 상태**다. 뺐다.

### 이걸 실패로 볼 것인가

솔직히 말하면 **미리 깐 게 아니라 성급했던 쪽에 가깝다.** "나중에 추천을 붙일 테니 자리를 만들어두자"는 판단이었는데, 그 나중이 오려면 데이터 수집이라는 훨씬 큰 문제가 먼저 풀려야 했다. 순서가 틀렸다.

다만 **뺀 판단은 옳았다.** 쓰지 않는 스키마는 공짜가 아니다. 마이그레이션마다 따라다니고, 읽는 사람에게 "이건 뭐지"를 계속 묻게 만든다. 추천은 여전히 하고 싶은 기능이고, 그때 다시 넣으면 된다.

## "그냥 써보고 싶었다"도 이유가 된다

Fastify를 골랐다. NestJS는 기본이 Express인데 어댑터를 갈아 끼웠다.

이유를 그럴듯하게 쓸 수는 있다. Fastify가 Express보다 빠르고, 스키마 기반 검증이 있고, 어쩌고. 그런데 **이 서비스 트래픽에서 그 차이는 측정도 안 된다.** 실사용자가 열 명이 안 된다.

진짜 이유는 하나다. **써보고 싶었다.**

개인 프로젝트의 특권이 이거라고 생각한다. 회사 코드였으면 "왜 기본값을 벗어나느냐"에 답할 수 있어야 하고, 답이 "궁금해서"면 통과 못 한다. 그런데 개인 프로젝트에서는 그게 충분한 이유다. **배우려고 만드는 것도 만드는 이유다.**

다만 이걸 성능 최적화였던 것처럼 포장하지는 않겠다. 그러면 다음에 진짜 성능 판단을 해야 할 때 스스로를 속이게 된다.

## `packages/types`에 값을 넣었다가 빌드가 깨진 이야기

공유 타입 패키지는 이렇게 생겼다.

```json
{
  "name": "@inos/types",
  "main": "./dist/index.js",
  "exports": {
    ".": {
      "import": "./dist/index.js",
      "require": "./dist/index.js",
      "types": "./dist/index.d.ts"
    }
  }
}
```

TMDB 이미지 URL을 만드는 헬퍼가 필요해서 여기에 넣었다. 타입이랑 같이 있는 게 자연스러워 보였으니까.

```
"TMDB_ATTRIBUTION" is not exported by "../../packages/types/dist/index.js"
```

**빌드가 깨졌다.**

원인은 `import`와 `require`가 **같은 파일**을 가리키는 데 있다. `tsc`가 뽑는 건 CommonJS인데 `exports.import`가 그걸 ESM인 것처럼 가리키니, Vite가 named export를 찾지 못한다. 타입은 컴파일 타임에만 존재하니 그동안 아무 문제가 없었고, **런타임 값을 처음 넣은 순간 드러났다.**

고친 방법은 듀얼 빌드를 붙이는 게 아니라 **값을 옮기는 것**이었다. 상수와 헬퍼는 `apps/web/src/lib/`로 가고, 패키지에는 타입만 남겼다.

> 이 패키지는 **타입 전용**이다. 지금은 그렇게 못 박아뒀다. 값이 필요하면 쓰는 쪽에 둔다.

## 인증은 세 번에 걸쳐 자랐다

한 번에 설계한 게 아니라 필요할 때마다 붙였다.

**1단계 — Google OAuth.** 가장 빨리 되는 것. 비밀번호를 저장하지 않아도 되니 보안 부담도 없다.

**2단계 — 리프레시 토큰.** 액세스 토큰만 쓰니 자꾸 로그아웃됐다. 로그인 유지 7일.

**3단계 — 로컬 로그인 + 초대 링크.** 이건 기능이 아니라 **관찰에서 나온 변경**이다. 이메일로 초대장을 보내는 방식이 기술에 덜 익숙한 멤버에게 실제 장벽이었다. 그래서 이메일/비밀번호 가입을 열고, 복사해서 메신저로 던질 수 있는 초대 링크를 만들었다.

닫힌 서비스라고 해서 **들어오는 문까지 어려울 필요는 없다.** 닫혀 있어야 하는 건 "누가 들어오는가"지 "어떻게 들어오는가"가 아니다.

## 배포는 EC2 한 대다

```
                     ┌──────────── EC2 한 대 ────────────┐
브라우저 ─ https ──▶ │ Caddy(:443) ─┬─ /api/*  → server   │
                     │              ├─ /ai/*   → ai-server│
                     │              └─ /*      → SPA      │
                     │ PostgreSQL ── Redis                │
                     └────────────────────────────────────┘
```

`master`에 머지되면 GitHub Actions가 타입체크를 돌리고, SSH로 들어가 `git reset --hard` 후 `docker compose up -d --build`를 친다. Caddy가 Let's Encrypt 인증서를 자동으로 발급하고 갱신한다.

**이유는 돈이다.** 실사용자가 열 명이 안 되는 서비스에 인스턴스를 여러 대 띄울 이유가 없다.

그리고 솔직히 말하면 **지금 상태도 이미 오버스펙이라고 생각한다.** 서버 둘, Redis, 큐, 컨테이너 여섯 개. 사용자 열 명한테 필요한 구성이 아니다.

그런데도 이렇게 둔 이유는 이게 **연습이기도 하기 때문**이다. 회사에서는 이미 굴러가는 인프라 위에 코드를 얹지, 인프라를 처음부터 세울 기회가 잘 없다. 배포 파이프라인을 직접 짜고, 리버스 프록시를 붙이고, 컨테이너가 왜 안 뜨는지 로그를 뒤지는 경험은 여기서만 할 수 있었다.

### 관측을 세 개 붙였다

SSH 없이 서버 상태를 보기 위해서다. 셋 다 **자격증명이 없으면 자동으로 비활성**이라 로컬 개발에 영향이 없다.

| 도구 | 용도 |
|---|---|
| **Sentry** | 서버 5xx와 프론트 런타임 에러를 스택트레이스와 함께 |
| **Grafana Cloud Loki** | `docker compose logs` 대신 웹에서 전체 컨테이너 로그 검색 |
| **UptimeRobot** | `/api/health`, `/ai/health` 5분 간격 감시 |

개인 프로젝트에 이걸 다 붙일 필요가 있느냐면 없다. 다만 붙여놓고 나니 **"터졌다"를 사용자보다 먼저 아는 상태**가 됐고, 그 차이는 생각보다 컸다.

## 그런데 여기에도 구멍이 있었다

배포 설정을 다 갖췄다고 생각했는데, 최근에 이런 걸 발견했다.

TMDB와 국립중앙도서관 API 키를 `.env.example`에 적어두고 EC2의 `.env`에도 채웠다. 그런데 **`docker-compose.yml`의 서버 `environment` 블록에 그 두 줄이 없었다.**

```yaml
services:
  server:
    environment:
      DATABASE_URL: ...
      JWT_ACCESS_SECRET: ...
      # TMDB_API_KEY 없음
      # SEOJI_CERT_KEY 없음
```

`.env`에 값이 있어도 **컨테이너 안으로 전달되지 않는다.** 프로덕션에서 작품 검색이 조용히 계속 503이었을 것이다.

타입체크도 통과하고 빌드도 통과하고 배포도 성공한다. **계층 사이의 빈칸은 컴파일러가 못 잡는다.**

이 시리즈에서 이런 종류의 실패가 계속 나온다. 큐 재시도를 설정했는데 안 돌고, 브로드캐스트 홉이 끊기고, 있는 API를 클라이언트가 안 부른다. 전부 **에러를 내지 않는 실패**다. 마지막 편에서 한 번에 모아보겠다.

## 정리

이 규모에 이 구조가 과한가? **과하다.** 사용자 열 명에게 서버 둘과 컨테이너 여섯은 필요 없다.

그런데 다시 만들어도 크게 다르지 않을 것 같다. 이 프로젝트는 서비스이기도 하지만 **인프라를 처음부터 세워보는 연습**이기도 했고, 그 목적에서는 과한 게 맞는 크기였다.

다만 구분은 해두려 한다. **모노레포는 지금도 이득이고**(맥락을 파일 시스템이 들고 있다), **서버 분리는 아직 값을 다 못 받았고**(1,349줄), **pgvector는 순서가 틀렸었다**(데이터가 먼저다). 셋을 뭉뚱그려 "잘 설계했다"고 쓰면 다음에 같은 실수를 한다.
