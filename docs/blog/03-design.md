# INOS 개발기 ③ — 화려함을 덜어내는 데 세 번이 걸렸다

> 인문학 모임 플랫폼 INOS를 4개월간 혼자 만든 기록. 총 5편.
>
> ① 기획 · ② 아키텍처 · **③ 프론트엔드와 디자인** · ④ Main server · ⑤ AI-server

---

프론트는 React 19 + Vite에 Tailwind v4, 상태는 TanStack Query와 zustand, 실시간은 socket.io. 12,495줄이다. 스택 이야기는 여기까지만 하겠다. 이 편의 주제는 그 위에 무엇을 그렸느냐다.

**시각 언어를 세 번 갈아엎었다.** 커밋으로 보면 이렇다.

| 언제 | 무엇 | 규모 |
|---|---|---|
| 2026-05-11 | `#ffdf05` 포인트 컬러 | 35파일 +1,554 |
| 2026-07-14 | 브루탈리스트 리디자인 | 38파일 +1,915 / −820 |
| 2026-07-22 | Claude Design 시안대로 랜딩 리뉴얼 | 2파일 +389 |
| 2026-09-08 | **흑백 디자인 시스템 전면 적용** | **85파일 +3,564 / −608** |

마지막이 압도적으로 크다. 그리고 이 글은 **왜 결국 색을 다 뺐는가**에 대한 이야기다.

---

## 1. 노란색으로 시작했다

첫 버전의 포인트 컬러는 `#ffdf05`였다. 쨍한 노랑.

이유는 딱히 없었다. 눈에 띄니까. 개인 프로젝트를 시작할 때 "우리 서비스 색"을 하나 정하고 싶은 마음이 있는데, 그게 이 노랑이었다.

돌아보면 이때는 **디자인을 하고 있지 않았다.** 색을 고르고 있었다.

## 2. 브루탈리스트로 갔다

두 번째는 브루탈리즘이었다. 두꺼운 테두리, 딱딱한 각, 강한 대비. 38파일을 고쳤고 820줄을 지웠다.

이건 나름 의도가 있었다. **"AI 서비스처럼 보이지 않기"**가 목표였다. 그때 기획 문서에 안티 레퍼런스를 이렇게 적어놨었다.

> - 보라색 그라디언트 AI 서비스 클리셰
> - 과도한 그림자와 글로우
> - Inter 폰트 + 회색 텍스트 + 파란 버튼 조합
> - "AI가 만들었다"는 느낌이 전면에 드러나는 UI

브루탈리즘은 저 목록의 정확히 반대편에 있다. 그래서 골랐다.

그런데 쓰다 보니 문제가 있었다. **읽기 불편했다.**

## 3. 랜딩만 다시 만들었다

세 번째는 규모가 다르다. **2파일, +389줄.** 랜딩 페이지 하나만 손봤다.

Claude Design으로 시안을 뽑아서 그대로 옮겼다. 결과는 좋았는데, 이때 이상한 상태가 됐다. **랜딩은 세련됐고 앱 안은 브루탈리스트였다.** 들어오는 문과 방 안의 언어가 달랐다.

그리고 히어로 이미지를 소파에서 책 읽는 마스코트 일러스트로 바꿨다. 이 마스코트가 나중에 **화면에서 색을 갖는 세 자리 중 하나**가 된다.

## 4. 그리고 전부 흑백으로

네 번째가 지금이다. 85파일, +3,564 / −608.

---

## 왜 결국 색을 다 뺐나

이유는 하나다. **INOS에서 화면의 주인공은 글이다.**

발제 질문, 멤버가 남긴 감상, 한줄평. 이 서비스를 쓰는 시간의 대부분은 읽는 시간이다. 모임 중에 발제문 화면을 띄워놓고 한 사람씩 답을 적는데, 그때 화면에 필요한 건 질문 하나뿐이다.

그런데 **색은 그 자체로 시선을 끈다.** 노란 버튼이 있으면 눈이 거기로 간다. 브루탈리즘의 두꺼운 테두리도 마찬가지다. 읽어야 하는 화면에서 그건 전부 방해다.

그래서 규칙을 네 줄로 정하고 85파일에 통과시켰다.

```
1. UI는 무채색 100%. 색은 작품과 마스코트에만.
2. 경계는 1px 헤어라인. 그림자 없음.
3. 위계는 크기와 굵기로만. 색으로 강조하지 않는다.
4. 랜딩까지 같은 팔레트. 예외 스코프 없음.
```

4번이 중요하다. **랜딩만 예쁘게 하는 걸 금지한 것**이다. 3번 국면에서 겪은 분열을 다시 만들지 않겠다는 뜻이다.

---

## 그런데 작품에는 색을 남겼다

여기가 이 시스템에서 제일 마음에 드는 부분이다.

UI에서 색을 전부 걷어내면 **책 표지와 영화 포스터만 색을 갖는다.** 화면에서 눈에 띄는 자리가 자동으로 "내가 읽은 것"에 몰린다.

①편에서 폐쇄형을 택한 세 번째 이유가 **허영**이라고 썼다. "우리끼리 이런 거 해"라고 말할 수 있는 것. 그 마음이 향하는 대상이 정확히 이 자리다. 내 서가에 꽂힌 책과 포스터.

그러니까 이건 미감의 문제가 아니라 **기획의 귀결**이다. 화면에서 가장 강한 자리를 무엇에 줄 것인가 — 버튼에 줄 수도 있었고 브랜드 색에 줄 수도 있었는데, 사용자가 자랑하고 싶어 하는 것에 줬다.

## 무채색으로 위계를 만드는 법

색을 못 쓰면 다른 축이 일해야 한다. 세 가지를 썼다.

### 명도 — 역할로 이름 짓기

```
paper     #fafafa → 다크 #0f0f0f    앱 바탕
surface   #ffffff → 다크 #171717    카드
surface-2 #f2f2f2 → 다크 #1f1f1f    한 단계 안쪽
ink       #141414 → 다크 #f2f2f2    본문
muted-2   #4a4a4a → 다크 #b5b5b5    본문 다음
muted     #6e6e6e → 다크 #8f8f8f    메타데이터
line      #e4e4e4 → 다크 #2e2e2e    1px 경계 전부
```

여기서 하나 짚고 싶은 게 있다. 라이트에서 `muted-2`는 `muted`보다 **어둡고**, 다크에서는 **밝다.** 두 모드 모두에서 `muted-2`가 "더 잘 읽히는 쪽"이라는 뜻이다.

**토큰 이름을 밝기가 아니라 역할로 지었기 때문에** 반전이 자동으로 맞는다. `gray-600` 같은 이름을 썼으면 다크 모드에서 전부 손으로 뒤집어야 했다.

### 굵기 — 위로 굵게가 아니라 아래로 얇게

```
font-bold      133회
font-semibold  123회
font-medium     71회
font-light      17회   ← 이게 특이하다
```

보통 강조할 때 굵게 한다. 이 시스템은 반대도 쓴다. **긴 설명문을 `font-light`로 내려서** 제목과의 간격을 벌린다. 위로 올릴 수 없으면 아래로 내리면 된다.

### 크기 — Tailwind 기본 스케일을 안 쓴다

```
text-[11px]  88회   섹션 라벨(대문자 + 자간), 메타
text-[13px]  44회   보조 본문
text-[15px]  23회   본문
```

`text-sm`, `text-base` 대신 px 임의값을 쓴다. 한국어는 같은 px에서 라틴보다 크게 보여서, 영문 기준으로 만들어진 기본 스케일이 잘 안 맞는다. 제목은 `clamp()`로 반응시킨다.

```
text-[clamp(38px,6vw,64px)]   랜딩 히어로
text-[clamp(28px,5vw,44px)]   페이지 제목
```

## 경고색을 없앤 대가

무채색 시스템에는 빨강을 둘 자리가 없다. 그래서 이렇게 됐다.

```css
--color-danger: #141414;    /* ink와 같은 값 */
```

**삭제 버튼이 본문과 같은 색이다.**

그럼 위험한 동작을 어떻게 알리느냐 — **문장과 확인 단계로 알린다.** 버튼 라벨을 정확히 쓰고, 필요하면 한 단계를 더 둔다.

이건 공짜가 아니다. 빨간 버튼은 한눈에 위험을 알리는데, 문장으로 알리려면 **문장을 잘 써야 한다.** 디자인 부담을 UX 라이팅 부담으로 옮긴 것이다.

지금 규모에서는 감당된다. 파괴적 동작이 많지 않으니까. 다만 이건 **결정이지 원칙이 아니라서**, 나중에 무섭게 알려야 할 동작이 생기면 다시 볼 자리다.

---

## 딱 하나 반전하지 않는 토큰

다크 모드 토큰을 짜다 보면 반드시 걸리는 함정이 하나 있다.

```css
--color-on-art: #141414;    /* 다크에서도 그대로 */
```

`on-art`는 **색칠된 면 위에 얹는 글자색**이다. 책등, 포스터 위의 텍스트.

이 면들은 **테마와 무관하게 자기 밝기를 갖는다.** 밝은 표지는 다크 모드에서도 밝다. 그런데 글자색이 테마를 따라 반전하면, 다크 모드에서 밝은 표지 위에 흰 글자가 올라가서 사라진다.

> **"무엇 위에 있는가"가 "어떤 테마인가"보다 우선하는 유일한 경우.**

토큰 하나에 주석을 길게 달아뒀다. 나중에 "왜 이것만 반전 안 하지" 하고 고칠 사람이 나 자신일 게 뻔해서.

## AI에게 디자인을 시킨다는 것

솔직하게 쓰겠다.

**무채색 토큰 체계는 내가 짜지 않았다.** 자연어로 명령만 했고 AI가 잡아줬다. 위에 나온 `paper` / `surface` / `surface-2` / `ink` / `muted` / `muted-2` / `line` 구조도, 다크 모드 대응도 그렇게 나왔다.

Claude Design도 써봤다. 경험은 좋았다. 다만 정직하게 말하면 **차이를 체감하진 못했다.** 이 프로젝트에서 요구한 디자인이 고난도가 아니어서, 일반적인 디자인 하네스 정도로도 이 수준은 나왔을 것 같다.

그럼 내가 한 건 뭔가. **결정이다.**

- 색을 뺀다는 결정
- 작품에만 색을 남긴다는 결정
- 랜딩에 예외를 두지 않는다는 결정
- 경고색을 포기하고 문장으로 대체한다는 결정

이 네 줄이 없으면 AI는 그냥 무난한 디자인을 만든다. **제약을 정하는 게 사람 몫이고, 그 제약 안에서 값을 채우는 건 AI가 훨씬 잘한다.** 이 프로젝트에서 디자인은 그렇게 나왔다.

## 한국어가 화면 밖으로 흘러나갔다

디자인 이야기 중에 가장 실무적인 버그다.

멤버가 쓴 긴 발제문이 **줄바꿈 없이 한 줄로 뻗어서 화면 밖으로 나갔다.** 실측했더니 600px 컬럼에서 `scrollWidth`가 **3,578**이었다.

범인은 `break-keep`이었다.

```css
word-break: keep-all;   /* Tailwind: break-keep */
```

한국어에서 흔히 쓰는 설정이다. 줄 끝에서 단어가 음절 중간에 잘리는 걸 막아주니까. 그런데 `keep-all`은 정확히는 **"공백만이 줄바꿈 기회"**라는 뜻이다.

한국어는 띄어쓰기 없이 입력되는 일이 잦다. 공백이 없으면 끊을 곳이 없고, 그러면 줄바꿈 대신 **가로로 넘친다.** 아이러니하게도 `break-keep`을 안 걸면 잘 감긴다 — CJK는 기본적으로 아무 두 글자 사이에서나 끊을 수 있기 때문이다.

동작하는 조합은 셋을 다 거는 것이다.

```
white-space: pre-wrap;      /* 입력한 줄바꿈 보존 */
word-break: keep-all;       /* 가급적 어절에서 끊기 */
overflow-wrap: break-word;  /* 그래도 안 되면 어쨌든 끊기 */
```

Tailwind로는 `whitespace-pre-wrap break-keep break-words`. 사용자 입력을 렌더링하는 모든 곳에 건다.

> 곁다리로 하나 더. **Tailwind는 소스 파일에서 발견한 클래스만 생성한다.** 후보 클래스를 런타임에 DOM으로 주입해서 테스트하면 조용히 아무 일도 안 일어난다 — CSS 자체가 만들어진 적이 없어서다. 검증은 인라인 스타일로 하고, 확정되면 소스에 써 넣어야 한다.

## 없는 데이터를 CSS로 만들었다

마지막이 이 시스템에서 가장 재미있었던 작업이다.

랜딩에 **서가**를 넣기로 했다. 책이 꽂힌 선반. 그런데 문제가 있었다.

**실제 책등 사진은 어떤 API에도 없다.** 출판사가 유통사에 넘기는 건 앞표지뿐이고, 책등은 애초에 디지털화되지 않는다. Google Books는 키 없이 쿼터가 막혔고, Open Library는 한국어 ISBN 네 건을 전부 404로 뱉었다. 국립중앙도서관 서지정보는 표지 URL이 거의 비어 있다(④편에서 숫자로 다시 나온다).

여기서 보통 "데이터가 없어서 못 합니다"가 된다. 대신 **책등의 구성 요소를 CSS로 재현하기로 했다.**

### 서른 벌

진짜 책등이 뭘로 이루어져 있는지부터 적었다.

- **장정 띠** 6종 — 없음 / 한 줄 / 두 줄 / 위만 / 제목 판 / 면 띠
- **질감** 3종 — 리넨 / 종이 / 광택 (전부 `repeating-linear-gradient`)
- **서체** 30종 — 명조·세리프(고전 양장), 고딕(인문 교양), 굵은 제목용(사회과학), 손글씨·붓글씨(시집·산문), 타자기
- **바닥 출판사 마크**, 모서리 처리, 명도 폭

명도는 흰색부터 먹색까지 넓게 잡고, 어두운 책등에는 밝은 글자를 얹었다. **무채색만으로 서른 권을 다르게 보이게 하려면 명도 폭이 넓어야 한다.**

### 한글 웹폰트 서른 벌의 무게

여기서 진짜 문제가 나온다. 한글 폰트 30개를 통째로 부르면 **CSS만 2,477,910 B**다. `@font-face` 조각이 3,843개. 랜딩에 얹을 수 있는 무게가 아니다.

Google Fonts의 `text=` 파라미터로 **실제 쓰인 글자만** 요청했다.

| | 전 | 후 |
|---|---:|---:|
| CSS | 2,477,910 B | **89,344 B** (−96.4%) |
| 폰트 파일 30개 | — | **676 KB** |

글자 목록은 제목에서 런타임에 뽑는다. 책을 추가해도 손으로 맞출 필요가 없다.

### 최적화가 만든 새 버그

여기서 끝이면 좋았을 텐데, **이 최적화가 새로운 실패 모드를 만들었다.**

랜딩은 책 목록이 고정이라 괜찮다. 그런데 실제 서재는 다르다. **책이 나중에 도착하고, 스크롤하면 20권씩 더 열린다.** 첫 요청 때의 글자만 받아뒀으면 나중에 열린 책은 폴백 글꼴로 떨어진다 — 서른 벌을 만든 의미가 그 지점에서 사라진다.

해법을 정하기 전에 먼저 재봤다. `text=` 응답이 `unicode-range`를 달고 오는지.

```css
@font-face {
  font-family: 'Gaegu';
  src: url(https://fonts.gstatic.com/l/font?kit=…) format('woff2');
  unicode-range: U+1103, U+1106, U+110b, …, U+c774, U+c778;
}
```

달고 온다. 그러면 여러 장의 스타일시트가 **글자 단위로 합쳐진다.** 그래서 전체를 다시 받는 대신 **모자란 글자만 증분 요청**하게 했다. 20권 → 30권으로 늘 때 추가 스타일시트 한 장, **970 B**.

> 성능 최적화는 "적용했다"가 아니라 "얼마였고 얼마가 됐다"로 말해야 한다. 그리고 최적화가 만든 새 실패 모드를 같이 막지 않으면 그건 최적화가 아니라 버그다.

---

## 같은 문제에 두 화면이 다른 답을 냈다

서른 벌 중 어느 벌을 입힐지 고르는 방법에서 갈렸다.

**랜딩**은 처음에 제목 해시로 골랐다. 그랬더니 `이방인`과 `자기만의 방`이 **나란히 같은 서체**로 떨어졌다. 32권을 한 줄로 늘어놓으면 인접 충돌이 눈에 띈다.

그래서 자리 순서로 돌렸다.

```ts
SPINE_STYLES[(index * 7 + 3) % 30]
```

7과 30이 서로소라 30권까지 한 벌도 겹치지 않고, 순서대로 나열되지도 않는다.

**실제 서재는 정반대 답이 나왔다.** 자리 순서로 고르면 **책 한 권 지울 때마다 뒤의 책이 전부 다른 얼굴이 된다.** 내 서재에서 "내 『데미안』은 저 어두운 명조 책"이라는 인식이 깨진다. 그래서 모임 id로 벌을 고정하되, 앞 권과 겹치면 한 칸 미는 방식으로 갔다.

```ts
let i = hash(seed) % 30;
if (i === prev) i = (i + 1) % 30;
```

> **"정체성 안정"과 "이웃 다양성"은 충돌하는 요구다.** 어느 쪽이 중요한지는 그 화면을 얼마나 자주 보느냐가 정한다. 스쳐 지나가는 랜딩은 다양성, 계속 돌아오는 서재는 안정성.

검증은 눈이 아니라 숫자로 했다. 서른 권 · 인접 중복 0 · 어두운 책등 14 · **글자 대비 최저 10.34:1**(WCAG AA 기준 4.5:1).

## 문서가 코드보다 빨리 썩는다

이 글을 쓰려고 `DESIGN.md`를 열었다.

**1안의 크림/인디고/앰버 팔레트가 그대로 있었다.** 코드는 그 뒤로 두 번 더 갈아엎혔는데 문서는 첫 팔레트에 멈춰 있었다.

```yaml
colors:
  parchment: "#FAFAF8"
  indigo-deep: "#2D3561"
  amber: "#C4872A"
```

넉 달 동안 아무도 이걸 안 읽었다는 뜻이다. 나 말고 읽을 사람이 없으니 당연하기도 한데, 문제는 **읽히지 않는 문서가 틀린 채로 남아 있으면 나중에 그걸 근거로 뭔가를 결정하게 된다**는 것이다.

이 시리즈를 쓰면서 `index.css`에서 역추출해 다시 썼다. 그리고 문서 맨 아래에 한 줄 박아뒀다.

> 토큰의 단일 출처는 `apps/web/src/index.css`다. 이 문서는 그것을 읽고 정리한 것이므로, 값이 바뀌면 코드가 먼저고 문서가 나중이다.

같은 정보를 두 곳에 두면 반드시 갈라진다. 갈라지지 않게 하는 방법은 **어느 쪽이 진실인지 문서에 적어두는 것**뿐이다.

## 곁다리 둘

**daisyUI가 사실상 안 쓰이고 있다.** `@plugin "daisyui"`로 로드는 되는데 테마 설정도 없고 컴포넌트 클래스도 거의 안 쓴다. 색·형태·타이포는 전부 커스텀 토큰이 결정한다. 초기에 붙였다가 자체 시스템으로 옮겨오면서 자연스럽게 안 쓰게 된 건데, **아직 안 걷어냈다.**

**Electron은 200줄이다.** 웹을 감싸는 얇은 래퍼고, `partition`으로 세션을 유지하는 게 거의 전부다. 데스크톱 앱이라기보다 "북마크 아이콘이 있는 브라우저 창"에 가깝다.
