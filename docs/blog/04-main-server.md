# INOS 개발기 ④ — 부모님이 이메일을 안 쓰셨다

> 인문학 모임 플랫폼 INOS를 4개월간 혼자 만든 기록. 총 5편.
>
> ① 기획 · ② 아키텍처 · ③ 프론트엔드와 디자인 · **④ Main server** · ⑤ AI-server

---

메인 서버는 7,438줄에 모듈 열둘이다. `auth`, `group`, `meeting`, `library`, `board`, `notification`, `mail`, `admin`, `user`, `seoji`, `tmdb`, `showcase`.

이 편은 그중 **"모임을 만들 수 있다"에서 "모임이 굴러간다"까지 무엇이 더 필요했는가**에 대한 이야기다. 그리고 그 필요를 알려준 건 대부분 코드가 아니라 사람이었다.

---

## 부모님께 써보시라고 드렸다

만들어놓고 자랑하고 싶어서 부모님께 링크를 보냈다.

**애초에 이메일을 안 쓰셨다.**

모임 초대장도, 날짜 확정 알림도, 발제문이 준비됐다는 소식도 전부 이메일로 보내고 있었다. 나에게 이메일은 기본값이다. 하루에 수십 통을 받고 알림도 켜져 있다. 그런데 **일반 사용자에게는 아니다.** 계정은 있지만 안 본다.

이걸 알기 전까지 나는 알림 시스템이 완성됐다고 생각했다. 트리거 네 개를 다 붙였고, 중복 방지도 넣었고, 지연 잡 스케줄링도 됐다. **기술적으로는 다 됐는데 사람에게 도달하지 않고 있었다.**

그래서 만든 게 **인앱 알림함**이다. 앱에 들어오면 놓친 알림을 몰아볼 수 있게. 이메일을 안 보는 사람에게도 소식이 닿는 두 번째 경로다.

### 그리고 "앱이 없다"는 것도 불편이었다

부모님이 말씀하신 또 하나가 이거였다. **브라우저 주소를 매번 치는 게 번거롭다.**

개발자에게 웹 앱은 앱이다. 북마크하면 되고, PWA로 설치하면 되고. 그런데 그건 **우리가 그렇게 훈련된 것**이지 모두가 그런 게 아니다. 홈 화면에 아이콘이 있는 것과 없는 것은 다른 물건으로 인식된다.

지금은 Electron으로 감싼 데스크톱 앱이 있다(③편에서 말한 200줄짜리). 모바일 네이티브 앱은 아직 없고, **만들어야 할 수도 있겠다는 가능성만 열어뒀다.**

> 이 두 가지는 코드 리뷰로는 절대 안 나온다. 만든 사람이 쓰면 안 보이고, **안 만든 사람이 써야 보인다.**

## 알림을 새 인프라 없이 만들었다

알림 트리거는 네 개다.

```prisma
enum NotificationType {
  DATE_CONFIRMED         // 날짜가 확정됐어요
  DISCUSSION_READY       // 발제문이 준비됐어요
  MEETING_REMINDER_3H    // 3시간 뒤에 모임이에요
  AVAILABILITY_REMINDER  // 아직 일정 응답을 안 하셨어요
}
```

전부 **기존 SMTP + BullMQ 위에** 올렸다. 새 시크릿도, 새 서비스도, 새 외부 의존도 없다.

### 중복 발송을 코드가 아니라 스키마로 막았다

같은 알림을 두 번 보내는 건 흔한 사고다. 잡이 재시도되거나, 스케줄이 겹치거나, 배포 중에 두 번 실행되거나.

보통은 애플리케이션에서 막는다. "보냈나?" 조회하고 안 보냈으면 보내고 기록하고. 그런데 **조회와 기록 사이에 다른 프로세스가 끼면 뚫린다.**

그래서 DB 제약으로 막았다.

```prisma
model NotificationLog {
  id        String           @id @default(uuid())
  meetingId String
  userId    String
  type      NotificationType
  sentAt    DateTime         @default(now())
  readAt    DateTime?        // 알림함에서 확인한 시각

  @@unique([meetingId, userId, type])
  @@index([userId, sentAt(sort: Desc)])
}
```

`@@unique([meetingId, userId, type])` — **"이 모임의, 이 사람에게, 이 종류의 알림"은 한 번뿐**이다. 두 번째 시도는 DB가 거절한다. 애플리케이션이 실수해도 데이터는 안 깨진다.

### 그리고 수신함은 이 테이블을 그대로 썼다

알림함을 만들려고 앉았을 때 처음 든 생각은 "알림 테이블을 새로 만들어야겠다"였다.

그런데 위 스키마를 다시 봤다. **중복 방지 원장이 이미 "누구에게, 무엇을, 언제 보냈는지"를 전부 기록하고 있었다.**

그러니까 수신함에 필요한 건 새 테이블이 아니라 **컬럼 하나**였다.

```prisma
readAt DateTime?   // null이면 안 읽음
```

`@@index([userId, sentAt(sort: Desc)])`도 이미 있었다. 사용자별 최신순 조회 — 수신함이 정확히 필요로 하는 인덱스다. 중복 방지를 위해 만든 인덱스가 목록 조회에 그대로 쓰였다.

> **새 메커니즘을 추가하기 전에 있는 것을 다시 볼 것.** 중복 방지 로그와 수신함은 다른 기능처럼 보이지만, 저장해야 하는 데이터가 같다.

### 지연 잡은 살아 움직인다

"3시간 전 리마인더"는 확정된 날짜 기준으로 예약한다. 그런데 **날짜가 바뀔 수 있다.**

- 날짜가 바뀌면 → 기존 잡을 취소하고 다시 예약
- 모임이 끝나거나 삭제되면 → 취소
- 일정 응답이 들어오면 → 그 사람의 독촉 리마인더 취소

예약해두고 끝이 아니라, **모임 상태가 바뀔 때마다 큐를 같이 손봐야 한다.** 이걸 안 하면 취소된 모임의 리마인더가 3시간 전에 날아간다.

## BullMQ에서 두 번 넘어졌다

### 1. jobId에 콜론을 못 쓴다

중복 잡을 막으려고 커스텀 jobId를 만들었다. `meeting:{id}:reminder` 같은 형태로.

```
Custom Id cannot contain :
```

BullMQ는 내부적으로 Redis 키를 콜론으로 조립한다. 그래서 jobId에 콜론이 들어가면 키 구조가 깨진다. 구분자를 바꿔서 해결했다. 별것 아닌데 **에러 메시지를 보기 전까지는 절대 예측할 수 없는 종류**다.

### 2. 재시도를 설정했는데 안 돌았다

이게 훨씬 중요한 실수다.

발제문 생성을 큐로 돌리면서 재시도 설정을 해뒀다. 실패하면 다시 시도하도록. 그런데 **한 번도 재시도되지 않았다.**

원인은 워커 안에서 생성 작업을 `await` 없이 던진 것이었다.

```
// 문제: 잡은 즉시 끝나고, 생성은 나중에 혼자 실패한다
worker(job => {
  generateDiscussion(job.data);   // await 없음
});                               // → 여기서 "성공"으로 종료
```

큐 입장에서는 **핸들러가 예외 없이 반환했으니 성공**이다. 실제 생성이 20초 뒤에 터져도 큐는 그걸 모른다. 재시도 설정은 있는데 발동할 계기가 영원히 안 온다.

고친 커밋 제목이 이거다.

```
fix: 발제문 생성을 동기 처리해 실패 시 큐 재시도가 실제로 동작하도록
```

> **"재시도를 설정했다"와 "재시도가 동작한다"는 다르다.** 이 시리즈에서 반복되는 주제의 첫 등장이다.

## 일정 조율 — 가장 많이 쓰이는 기능

만든 기능 중에 **실제로 검증된 게 이거 하나**다.

### when2meet을 그대로 베끼지 않았다

when2meet은 30분 격자에 드래그로 색칠한다. 처음엔 그렇게 만들려다 말았다.

월간 모임에서 필요한 정보는 두 가지뿐이다. **며칠이 되는가**, 그리고 **저녁이 나은가 낮이 나은가**. 30분 단위 격자는 이 두 가지를 얻기에 과한 UI다.

그래서 쪼갰다. **날짜는 격자로 고르고, 선호 시간은 별도 텍스트로 적는다.** 도구를 참고하되 자기 맥락에 맞게 줄인 것이다.

### 자동 확정은 "전원 가능"만

```ts
// 전원 가능한 날짜만 자동 확정 (동률이면 가장 빠른 날). 없으면 null → 소유자가 수동 확정.
private computeConfirmedDate(availabilities, from, to): string | null {
  const counts = this.countDates(availabilities, from, to);
  const unanimous = Array.from(counts.entries())
    .filter(([, c]) => c >= availabilities.length)
    .map(([d]) => d)
    .sort();
  return unanimous[0] ?? null;
}
```

로직 자체는 단순하다. **응답한 사람 수와 같은 날짜만** 통과. 동률이면 가장 빠른 날.

중요한 건 `?? null`이다. **자동으로 안 되는 경우를 정상 흐름으로 뒀다.**

### 그리고 안 되는 경우가 훨씬 잦다

써보니 **모두의 일정이 한 번에 맞는 날이 거의 없다.** 네 명만 돼도 그렇다.

그래서 수동 확정 경로가 실질적인 주 경로가 됐다. 겹치는 날이 없으면 소유자에게 메일이 가고, 소유자는 날짜별 인원을 보고 직접 정한다.

이 구조가 예상 못 한 케이스들도 받아줬다.

- **"나 한번만 해볼래" 하고 게스트로 끼는 사람** — 정식 멤버가 아니라 응답 집계에 안 잡히는데, 수동 확정이라 상관없다
- **투표를 안 해서 따로 물어본 경우** — 메신저로 물어보고 소유자가 그 답을 반영해 확정한다

> **자동화가 안 되는 경로를 예외가 아니라 정상 흐름으로 만들어두면, 예상 못 한 케이스가 거기로 흘러든다.** 자동 확정만 만들고 "안 되면 어쩌지"를 나중으로 미뤘으면 지금쯤 막혔을 것이다.

## 메일이 스팸으로 간다

정직하게 쓸 문제가 하나 있다.

**개인 Gmail SMTP로 보내고 있다.** 앱 비밀번호를 발급받아 붙인 구성이고, 초대장·확정 알림·리마인더가 전부 여기서 나간다.

**스팸함으로 들어가는 일이 있다.** 원인은 뻔하다 — SPF/DKIM/DMARC가 서비스 도메인 기준으로 정렬돼 있지 않고, 발신자 평판도 없다.

정석은 SendGrid나 SES 같은 발송 전용 서비스에 도메인을 인증해 붙이는 것이다. 아직 안 했다. **도달률을 측정할 만큼 사용자가 없기 때문**이다. 표본이 열 명이 안 되는데 도달률을 논하는 건 의미가 없다.

그나마 다행인 건 **발신 주소가 실제 내 메일**이라는 점이다. 받는 사람이 아는 주소라 스팸함에서 찾아낼 여지가 있다. 임시방편이지 해결은 아니다.

> 사용자가 늘면 가장 먼저 손봐야 할 자리다. **초대장이 안 닿으면 폐쇄형 서비스는 아예 시작이 안 된다.**

## 외부 데이터를 붙이면서 배운 것

이 서비스에는 오랫동안 **작품 이미지나 메타데이터가 하나도 없었다.** 제목과 저자를 손으로 치는 게 전부였다.

최근에 TMDB(영화)와 국립중앙도서관 서지정보(도서)를 붙였다.

### 유니크 키 하나가 중복 제거이자 캐시다

```prisma
model MovieWork {
  tmdbId    Int      @unique
  fetchedAt DateTime @default(now())
  ...
}
```

```ts
const REFETCH_AFTER_MS = 30 * 24 * 60 * 60 * 1000;   // 30일

if (existing && Date.now() - existing.fetchedAt.getTime() < REFETCH_AFTER_MS) {
  return existing;                    // 캐시 히트 — API 안 부름
}
return this.prisma.movieWork.upsert({ ... });
```

같은 영화를 여러 모임이 골라도 행은 하나다. 그리고 **그 행이 TMDB 호출의 캐시 역할을 겸한다.** 별도 캐시 계층이 필요 없다. 30일이 지나면 다시 받는다.

### 그런데 책은 안 됐다

영화는 TMDB가 잘 준다. 포스터도, 감독도, 장르도. **책이 문제였다.**

국립중앙도서관 서지정보에 실제 인증키를 넣고 재봤다.

| 검색어 | 총 건수 | 표지 URL 있는 것 |
|---|---:|---:|
| 소년이 온다 | 25 | **0** |
| 사피엔스 | 309 | **0** |
| 이방인 | 1,308 | **0** |

**표지가 0건이다.** 그리고 부분 일치 검색이라 이런 게 걸린다.

- `급류` → *물리박사 물갈퀴의 급류수학*
- `채식주의자` → *왜 채식주의자인가*
- `데미안` 검색 3번째 → *(알타미라 벽화에서 데미안 허스트까지) 미술법*

무엇보다 **서지 검색이라 랭킹 개념 자체가 없다.** "인기 있는 책"을 뽑을 방법이 없다.

### 붙이기 전에 재보고 접었다

원래 계획은 랜딩 서가를 이 API로 자동으로 채우는 것이었다. **위 숫자를 보고 접었다.**

사람이 후보를 보고 고르는 **자동완성에는 충분하다.** 이방인을 검색하면 알베르 카뮈 판이 첫 결과로 온다(완전 일치 → 접두 일치 → 부분 일치 순으로 정렬을 넣었다). 그런데 사람 없이 목록을 채우면 엉뚱한 책이 서가에 꽂힌다.

그래서 웹이 이미 들고 있던 큐레이션 목록을 **폴백이 아니라 정식 출처로 승격**했다.

> ②편에서 추천 기능 때문에 pgvector를 깔았다가 데이터 수집 문제로 걷어낸 이야기를 썼다. **넉 달 뒤에 같은 벽에 다시 부딪혔다.** 이번엔 붙이기 전에 재봤다는 게 다르다.

### 저자 이름을 정리하는 데 정규식 다섯 단계가 들었다

서지정보의 `AUTHOR` 필드는 역할이 한 덩어리로 온다.

```
저자 : 헤르만 헤세;역자 : 이민정;
아이작 아시모프 지음 ;이강환 옮김
알베르 카뮈 [저] ; 김용훈 [역]
글/그림: Ryuhei Tamura ;번역: 김수연
글 김성훈, 그림 최복기, 감수 오창길
Bohra Naono  번역:김명은
```

자동완성 한 줄에 번역가와 삽화가와 낭독자까지 나오고 있었다. 대표 저자만 남기는 정리 함수를 짰고, 실측한 **19가지 형태를 전부 통과**시켰다.

한 번 틀렸던 케이스가 재미있다. `글/그림: Ryuhei Tamura ;번역: 김수연`이 **`글/`만 남았다.** 부차 역할(`그림:`)을 먼저 잘랐더니 앞 라벨 안에 있는 `그림:`에 걸린 것이다. **라벨 제거를 순서상 앞으로 옮겨서** 고쳤다.

> 문자열 정리에서 순서는 로직이다. 같은 규칙을 다른 순서로 적용하면 다른 답이 나온다.

## 아무도 부르지 않는 API가 있었다

마지막이 이 편에서 제일 뼈아픈 발견이다.

서버는 `bookIsbn`을 받으면 국립중앙도서관에서 책을 확정해 `book_works`에 적재하는 경로를 갖고 있다. **모임 생성·수정·재시도 세 곳 모두에.**

그런데 **웹이 한 번도 그 경로를 호출하지 않았다.** 영화는 TMDB 검색으로 골라서 `movieTmdbId`를 보내는데, 책만 제목과 저자를 손으로 쳐서 문자열로 보내고 있었다.

즉 **`bookWork`가 붙은 모임이 하나도 없었다.** 서버 코드는 멀쩡히 존재했고, 테스트를 했다면 통과했을 것이고, 아무도 안 썼다.

이걸 발견한 게 최근이고, 고치면서 프론트에 도서 검색 자동완성을 붙였다.

### 배포 설정에도 같은 구멍이 있었다

TMDB와 서지정보 API 키를 `.env.example`에 적어두고 EC2의 `.env`에도 채웠다. 그런데 **`docker-compose.yml`의 서버 `environment` 블록에 그 두 줄이 없었다.**

`.env`에 값이 있어도 컨테이너 안으로 전달되지 않는다. **프로덕션에서 두 검색이 조용히 계속 503이었을 것이다.**

타입체크 통과, 빌드 통과, 배포 성공. **계층 사이의 빈칸은 컴파일러가 못 잡는다.**

## 정리

이 편에서 만든 것들을 다시 보면 공통점이 있다.

**알림함**은 이메일을 안 보는 사람이 있다는 걸 알고 만들었다.
**로컬 로그인과 초대 링크**는 이메일 초대가 장벽이라는 걸 알고 만들었다(②편).
**수동 확정 경로**는 일정이 안 맞는 게 정상이라는 걸 알고 남겨뒀다.

전부 **기능 목록에서 나오지 않고 사용에서 나왔다.** 그리고 그 사용은 대부분 내가 아니라 남이 한 것이었다.

반대로 이 편의 실패들도 공통점이 있다. 큐 재시도, 죽은 ISBN 경로, 빠진 환경변수 — **셋 다 에러를 내지 않는다.** 로그에도 안 남고 모니터링에도 안 잡힌다. 누가 "이거 왜 안 되지"라고 물어봐야 비로소 보인다.
