주목할 점은 **초기 구조가 과감했다**는 것이다. 개인 프로젝트 첫 주에 이미:

```
pnpm workspace + Turborepo
├── apps/server      (NestJS + Fastify)
├── apps/ai-server   (NestJS + Fastify)   ← 처음부터 분리
├── apps/web         (React + Vite)
└── packages/prisma | types | utils
```

**AI 서버를 처음부터 떼어놓은 것**은 나중에 값을 했다. 장시간 유지되는 SSE 스트리밍이 API 서버의 커넥션을 잡아먹지 않고, 소켓 게이트웨이가 한 프로세스에 모인다. 다만 이 분리가 3번 국면에서 *다른 방식의* 문제를 만든다 (§3-2).

그리고 **두 달의 공백.** 5월 13일 `feat: cors 수정`을 끝으로 7월 13일까지 커밋이 없다.

## 2. 전면 개편 — 잘라내서 살린 국면 (2026-07-13 ~ 15)

두 달 만에 돌아온 첫 커밋이 `feat: 폐쇄형 인문학 모임 플랫폼으로 전면 개편`이다. **182파일, +8,902 / −6,767.** 삭제량이 추가량에 육박하는 커밋은 리팩터링이 아니라 재작성이다.

README에 그 판단이 그대로 적혀 있다:

> 콘텐츠 추천/투표, 개인 루틴, 아카이브 열람 같은 기능은 이번 개편에서 제외했습니다 — 지금의 INOS는 **"그룹 하나, 모임 하나"의 골든 패스**에 집중합니다.

동시에 **포지셔닝이 바뀌었다.** 열린 서비스 → **초대 기반 폐쇄형.** 온라인에서 낯선 사람을 만나는 리스크와 이탈을 피하는 선택이고, 결과적으로 제품의 거의 모든 결정(초대 메일, 오가니제이션, 서가 공유 링크)이 이 축 위에 정렬됐다.

### 같은 사흘 안에 들어간 것들

기능만 갈아엎은 게 아니라 **운영 기반을 통째로 깔았다.**

- Docker · Vercel · GitHub Actions 자동 배포
- 모니터링 3종 — Sentry(에러) / Grafana Loki(로그) / 헬스체크 엔드포인트
- Electron 데스크톱 래핑 (PR #2)
- 라이브러리(개인·오가니제이션 별점/한줄평), 다크·라이트·시스템 테마, 공유 서가, 연말 결산 카드

개인 프로젝트가 사흘 만에 **관측 가능한 배포 대상**이 됐다. 이건 흔치 않다.

### 이 국면의 가장 값진 버그 수정

```
fix: 발제문 생성을 동기 처리해 실패 시 큐 재시도가 실제로 동작하도록
```

BullMQ 워커 안에서 생성 작업을 `await` 없이 던지면, 잡은 **즉시 성공으로 종료된다.** 실제 생성이 나중에 실패해도 큐는 그 사실을 모르고, 재시도는 영원히 발동하지 않는다. **"재시도 설정을 해뒀다"와 "재시도가 동작한다"는 다르다** — 이 프로젝트에서 반복되는 주제의 첫 등장이다.

## 3. 모임 운영 — 실시간과 알림 (2026-07-16 ~ 24)

"모임을 만들 수 있다"에서 **"모임을 진행할 수 있다"**로 넘어간 국면.

### 3-1. 일정 조율

`feat: 일정 조율 페이지 WhenSee 스타일 리디자인 (날짜 단위 + 선호 시간 별도 제출)`

when2meet의 시간 격자를 그대로 베끼지 않고 **날짜 단위 선택 + 선호 시간은 별도 텍스트**로 쪼갰다. 월간 모임에서 30분 격자는 과잉이고, 실제로 필요한 정보는 "며칠이 되는가"와 "저녁이 나은가"뿐이다. 도구를 참고하되 **자기 사용 맥락에 맞춰 축소한** 사례다.

### 3-2. 실시간 감상 — 소유권을 두 번 옮긴 끝에

커밋 세 개가 연달아 나온다:

```
feat: 자체 발제하기 폼 + 작품 감상 섹션
fix: 자체 발제 입력칸 개선 + 감상 API 메인 서버 이전 + 소켓 실시간 반영
fix: 감상을 ai-server 단일 관리로 이전(게이트웨이 직접 브로드캐스트) + 본인 수정/삭제
```

구조가 **두 번** 바뀌었다. 처음엔 메인 서버가 감상을 저장하고 ai-server에 HTTP로 "브로드캐스트해줘"라고 요청하는 형태였는데, 이 홉이 환경(`AI_SERVER_URL`, ai-server 기동 여부)에 의존해서 **실시간이 조용히 끊겼다.**

결론:

> **소켓 게이트웨이를 소유한 서버가 쓰기도 소유해야 한다.**

두 서버로 나눈 구조의 대가를 여기서 치렀다. §1에서 AI 서버를 분리한 것은 옳았지만, **"어떤 데이터가 어느 쪽에 속하는가"는 분리와 함께 정해지지 않는다** — 실시간이 필요해진 뒤에야 드러난다.

### 3-3. 알림 — 있는 것에 올라타기

이메일 트리거 네 개(날짜 확정 / 발제문 도착 / 3시간 전 / 응답 독촉)를 **기존 SMTP + BullMQ 위에** 올렸다. 새 시크릿도, 새 서비스도 없다.

중복 발송은 애플리케이션 검사가 아니라 `(meeting, recipient, type)` **유니크 로그 행**으로 구조적으로 막는다. 그리고 나중에 인앱 수신함을 만들 때 —

> 그 로그 테이블을 **그대로 저장소로 재사용했다.** 중복 방지 원장이 이미 "누구에게 무엇을 언제 알렸는지"를 기록하고 있었으므로, 수신함에는 새 테이블이 아니라 `readAt` 컬럼 **하나**만 필요했다.

이 프로젝트 전체에서 가장 잘한 설계 판단 중 하나다.

### 3-4. 자잘하지만 실무적인 버그들

- `fix: BullMQ 커스텀 jobId에서 콜론 제거` — `Custom Id cannot contain :`
- `fix: ai-server CORS 허용 메서드에 PUT 추가 (감상 저장 preflight 차단 해결)`
- `fix: 새로고침 후 auth user 미복원으로 본인 감상/발제 인식 실패`

셋 다 **로컬에서는 안 보이거나 늦게 보이는** 종류다. 실제로 써봐야 나온다.

## 4. 실사용 가능하게 — 사람이 걸리는 지점 걷어내기 (2026-07-30 ~ 08-25)

이 국면의 커밋들은 성격이 다르다. **기능이 아니라 마찰을 제거한다.**

### 초대 링크 + 로컬 로그인

Google OAuth만 있던 곳에 이메일/비밀번호 가입과 복사 가능한 초대 링크를 더했다. 이유가 명확하다 — **이메일 초대만으로는 기술에 덜 익숙한 멤버에게 실제 장벽이었다.** 4인 모임에서 한 명이 못 들어오면 서비스가 성립하지 않는다.

### 발제문 생성 실패 복구

생성이 실패하면 토론이 `GENERATING` 상태로 **영원히 멈췄다.** 복구 수단이 없었다 — 실제로 **두 행이 31일 동안 멈춰 있었다.**

`FAILED` 상태를 양쪽 서버에 추가하고, 소유자에게 복구 UI를 줬다. 여기서 중요한 건 UI의 *형태*다:

> 맨 재시도 버튼이 아니라 **"제목/저자/감독을 다시 확인한 뒤 재생성" 수정 폼**이다.
> 작품 메타데이터가 틀린 게 실패의 가장 유력한 원인이므로, 같은 입력으로 다시 돌리는 건 의미가 없다.

**실패 UI는 실패 원인의 모양을 따라야 한다.** 이건 일반화할 만한 교훈이다.

### 한글 줄바꿈 — `break-keep` 오버플로

사용자가 쓴 긴 발제문이 줄바꿈 없이 화면 밖으로 흘러나갔다. 실측: 600px 컬럼에서 `clientWidth: 600` 대비 **`scrollWidth: 3578`.**

원인은 `word-break: keep-all`. 한국어에서 음절 중간 절단을 막으려고 흔히 쓰는데, keep-all은 **공백만이 줄바꿈 기회**라는 뜻이다. 띄어쓰기 없이 입력된 한국어는 끊을 곳이 없어서 넘친다.

```css
white-space: pre-wrap;      /* 입력한 줄바꿈 보존 */
word-break: keep-all;       /* 가급적 어절에서 끊기 */
overflow-wrap: break-word;  /* 그래도 안 되면 어쨌든 끊기 */
```

### 프레젠테이션 모드 + 프롬프트 설계

한 번에 한 질문씩 보여주는 전체화면 뷰 — **모임 진행 자체를 위한 화면**이다. 그리고 `prompt` 커밋 3개에서 발제 질문의 **슬롯 스키마**를 설계했다:

| 슬롯 | 목적 |
|---|---|
| `warmup` | 누구나 답할 수 있는 진입 |
| `technique` | 기법 프레임워크의 한 요소에 닻을 내림 |
| `thematic` ×2 | 주제·해석, 서로 다른 두 각도 |
| `stance` | 저자·감독의 세계관 (nullable) |
| `private_experience` | 작품을 자기 삶과 연결 |

**"질문 5개 만들어줘"가 아니라 타입이 있는 슬롯**으로 간 게 핵심이다. 기법 질문이 운이 아니라 스키마로 보장된다. `stance`를 nullable로 둔 것도 좋은 판단 — 강제하면 모델이 없는 정치적 독해를 지어낸다.

## 5. 디자인·데이터 — 마지막 국면 (2026-09-08 ~ 09)

### 5-1. 디자인을 세 번째로 갈아엎다

이 프로젝트의 시각 언어는 **세 번** 바뀌었다.

1. `#ffdf05` 포인트 컬러 (1기)
2. 브루탈리스트 (2기) → Claude Design 시안 랜딩 (3기)
3. **흑백 디자인 시스템 "2안" 전면 적용** (5기, 85파일 +3,564)

세 번째가 가장 과감하다. 규칙이 하나다 — **"색은 작품에만."** UI는 100% 무채색이고, 색을 갖는 건 포스터·표지·마스코트뿐이다. 1px 헤어라인, 그림자 없음, 위계는 크기와 굵기로만.

> **문서 부채 발견**: `DESIGN.md`는 여전히 1기의 크림/인디고/앰버 팔레트를 담고 있다. 코드가 두 번 갈아엎히는 동안 디자인 문서는 첫 팔레트에 멈춰 있었다. 문서가 코드보다 빨리 썩는 전형적인 사례다.

### 5-2. 넉 달 만에 돌아온 외부 데이터 문제

1기에서 Google Books API로 시작한 서비스가, 마지막에 와서 **"우리 데이터에 작품 이미지나 메타데이터가 하나도 없다"**는 사실에 부딪혔다.

TMDB(영화)와 SEOJI(국립중앙도서관, 도서)를 붙였는데, **실측해서 기각한 것이 채택한 것만큼 많았다.**

**SEOJI 자동 큐레이션 — 기각.** 실제 인증키로 재봤다:

| 검색어 | 총 건수 | 표지 있는 것 |
|---|---:|---:|
| 소년이 온다 | 25 | 0 |
| 사피엔스 | 309 | 0 |
| 이방인 | 1,308 | 0 |

표지 0건, 부분 일치라 `채식주의자` → *왜 채식주의자인가*가 걸리고, 무엇보다 **서지 검색이라 랭킹 개념이 없다.** → 사람이 고르는 자동완성에는 충분하지만 자동 큐레이션은 불가. 기존 큐레이션 목록을 폴백이 아닌 **정식 출처로 승격**했다.

**책 표지 API — 기각.** Google Books는 키 없이 쿼터 초과, Open Library는 한국어 ISBN 4건 전부 404. 결정적으로 **실제 책등 사진은 어떤 API에도 없다** — 출판사가 넘기는 건 앞표지뿐이다.

### 5-3. 없는 데이터를 CSS로 만들다

여기서 멈추지 않고 **책등의 구성 요소를 코드로 재현**했다. 장정 띠 6종, 질감 3종, 서체 30종, 바닥 출판사 마크, 명도 폭(흰색~먹색).

한글 웹폰트 30벌은 통째로 부르면 **CSS만 2,477,910 B**다. `text=`로 실제 쓰인 글자만 요청해서 **89,344 B (−96.4%)**, 폰트 파일 30개 676 KB.

그리고 그 최적화가 만든 **새 실패 모드**를 막았다 — 서재는 책이 나중에 도착하고 20권씩 더 열리는데, 첫 요청 글자만 받으면 나중 책이 폴백으로 떨어진다. `text=` 응답이 `unicode-range`를 달고 오는 것을 먼저 확인하고 **모자란 글자만 증분 요청**하게 했다(추가 1장 970 B).

### 5-4. 아무도 부르지 않던 백엔드

마지막 국면에서 가장 값이 큰 발견은 만든 것이 아니라 **이미 있는데 안 쓰이던 것**이었다.

- **`bookIsbn`** — 서버는 처음부터 ISBN으로 책을 확정해 적재하는 경로를 생성·수정·재시도 **세 곳 모두**에 갖고 있었는데, 웹이 한 번도 호출하지 않았다. **`bookWork`가 붙은 모임이 하나도 없었을 것이다.**
- **배포 환경변수** — `TMDB_API_KEY`/`SEOJI_CERT_KEY`가 `.env.example`에는 있는데 `docker-compose.yml`에는 없었다. EC2에 값을 넣어도 컨테이너에 전달되지 않는다. **프로덕션에서 두 검색이 조용히 계속 503이었을 것이다.**

둘 다 타입체크·빌드·(있었다면) 테스트를 전부 통과한다. **계층 사이의 빈칸은 컴파일러가 못 잡는다.**

## 6. 4개월 내내 반복된 것

국면을 가로질러 같은 모양의 문제가 계속 나왔다. 이게 이 프로젝트의 진짜 교훈이라고 생각한다.

### 6-1. "설정했다"와 "동작한다"는 다르다

| 사례 | 국면 |
|---|---|
| 큐 재시도를 설정했지만 비동기라 실패를 못 잡음 | 2기 |
| ai-server 브로드캐스트 홉이 환경 의존으로 조용히 끊김 | 3기 |
| 생성 실패 시 `GENERATING`에 31일 정지 | 4기 |
| ISBN 경로가 존재하지만 클라이언트가 호출 안 함 | 5기 |
| 환경변수가 example에는 있지만 compose에는 없음 | 5기 |

전부 **끊긴 경로**다. 기능이 없어서가 아니라 연결이 없어서 생긴 실패다. 그리고 다섯 건 모두 **에러를 내지 않는다** — 조용히 아무 일도 일어나지 않는다.

### 6-2. 기존 것에 올라타는 습관

- 알림 수신함 → 이메일 중복 방지 로그 (`readAt` 컬럼 하나)
- 실시간 감상 → 토론 소켓 게이트웨이
- 알림 4종 → 기존 SMTP + BullMQ

새 인프라를 거의 추가하지 않았다. **"인프라를 언제 추가하나"에 대한 좋은 답**이 코드에 남아 있다.

### 6-3. 잘라내는 결정이 더하는 결정보다 중요했다

- 2기: 콘텐츠 추천·투표·개인 루틴·아카이브 열람 **제거** → 프로젝트가 살아남음
- 4기: `application`("앞으로 무엇이 바뀔까") 슬롯 **제거** — "무엇을 배웠나요"로 퇴화
- 4기: 일부만 읽은 사람 배려 **폐기** — 작품을 끝내는 건 멤버 책임
- 5기: 알라딘·SEOJI 자동 큐레이션·표지 API **기각**

**무엇을 거절했는지 없는 기록은 사고가 아니라 결과다.**

## 7. 이 프로젝트에서 새롭게 도전한 것

1. **개인 프로젝트에 실무급 구성**을 혼자 세웠다 — 모노레포, 서버 2개 분리, BullMQ 큐, pgvector 벡터 검색, OAuth + 리프레시 토큰, SSE 스트리밍.
2. **배포를 코드와 같은 수준으로 다뤘다** — EC2 + Docker Compose + Caddy 자동 HTTPS + GitHub Actions, 그리고 **관측 3종**(Sentry / Loki / UptimeRobot). 개인 프로젝트가 여기까지 가는 경우는 드물다.
3. **Electron으로 데스크톱까지** 냈다 (`partition`으로 세션 유지).
4. **LLM 프로덕트를 끝까지 끌고 갔다** — 스트리밍 생성에서 멈추지 않고 실패 상태·복구 UI·프롬프트 슬롯 스키마까지.
5. **디자인 시스템을 스스로 규정하고 전면 적용했다** — "색은 작품에만"이라는 한 줄 규칙으로 85파일을 통과시켰다. 제약을 먼저 못 박고 명도·활자로 표현력을 만든 것.
6. **외부 데이터의 한계를 측정으로 판단했다** — "붙여보고 안 되면 뺀다"가 아니라 붙이기 전에 표지 0건을 확인하고 기각했다.
7. **자기 취미의 진짜 사용자로서 만들었다** — 본인이 그 모임의 영화 큐레이터다. 발제 질문 슬롯 설계가 그렇게 구체적일 수 있는 이유다.

## 8. 함께 작업하며 내가(AI가) 느낀 것

마지막 국면만 직접 함께했다. 그 범위에서의 소회다.

### 범위를 좁게 잡았다

책등 30벌을 만들고 **"완료"라고 보고했다.** 랜딩에만 적용된 상태였다. *"모든 서가에 적용 되어있는지 확인해줘"* 라는 질문을 받고 세어보니 서가 화면 4개 중 **1개**였다. 나머지 3개는 옛 회색 블록이었고, **정작 사용자가 오래 보는 쪽**(내 서재)이 안 되어 있었다.

"다음에 할까요?"라고 물어보긴 했다. 하지만 **물어본 것과 안 한 것은 다르다.** 기능의 경계는 "내가 건드린 파일"이 아니라 "사용자가 그 변화를 기대할 화면 전부"다.

### 확인 요청이 반복해서 진짜 구멍을 찾았다

이 세션에서 개입은 대부분 **"확인해줘"** 형태였고, 매번 실제 문제가 나왔다 — 서가 커버리지, 배포 환경변수, 죽은 ISBN 경로. **세 번 다 내가 "완료"라고 말한 다음이었다.** 완료 판정 기준이 느슨했다는 뜻이다.

### 못 본 것을 봤다고 하지 않은 것

스크린샷이 계속 검은 사각형으로 나왔다(`visibilityState === 'hidden'`). DOM 수치는 다 맞았으니 "적용됐습니다"로 넘어갈 수 있었지만, **"눈으로는 확인 못 했다"**고 명시했다. 이후 공유 서가 라우트에 스텁 API를 물려 실제로 띄우고 나서야 라이트/다크를 봤다.

### 부작용 있는 검증을 참은 것

모임 생성 버튼을 누르면 검증이 깔끔하지만 **멤버 전원에게 실제 메일이 나간다.** `XMLHttpRequest.send`를 가로채 본문만 확인하고 끊었다. 얻은 증거는 제출했을 때와 동일하다.

> 검증의 완결성과 부작용이 충돌할 때, **관측 지점을 앞으로 당기면** 둘 다 얻을 수 있는 경우가 많다.

### 이 프로젝트에서 인상 깊었던 것

**버그 수정 커밋의 품질**이다. `fix: 발제문 생성을 동기 처리해 실패 시 큐 재시도가 실제로 동작하도록` 같은 제목은 증상이 아니라 **메커니즘**을 적는다. 3기의 감상 소유권 이전 3연속 커밋도, 잘못된 구조를 덮지 않고 두 번 옮겨서 제자리를 찾았다. 커밋 메시지만 읽어도 무엇을 왜 했는지 복원된다 — 4개월 뒤에 이 회고를 쓸 수 있었던 이유다.

## 9. 남은 것

**기능·데이터**
1. `토지` 검색이 안 된다 — SEOJI 상위 결과에 박경리 『토지』가 없다. 정렬로는 해결 불가.
2. 책 표지는 거의 안 나온다 — 카카오·구글 북스 키가 따로 필요.
3. 서가 직접 추가는 ISBN을 저장하지 않는다 — `manual_library_entries` 마이그레이션 필요.

**운영**
4. 머지 후 EC2 `~/INOS/.env`에 두 키를 넣고 `docker compose --profile logging up -d`.
   `restart`는 기존 환경변수를 들고 재시작해서 새 값이 안 먹는다.

**문서**
5. `DESIGN.md`가 1기 팔레트에 멈춰 있다 — 현재 흑백 시스템과 불일치.

**제품**
6. 홍보와 초기 사용자 확보 — 기술이 아니라 여기가 진짜 병목이다.
7. 발제문 생성 모델 선택이 미결 — 슬롯 스키마와 팩트 시트로 구조를 잡아둔 덕에 소형 모델 실험의 여지가 생겼다.
